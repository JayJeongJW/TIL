# 2026-11-01 QA 수업 정리 — 펫 시스템 상세명세서 실습과 기획서 리딩 회고

> 개인 강의 필기와 실습 회고. 강사 설명·피드백, 다른 수강생 작성본에서 배운 점, 본인의 해석과 향후 실천 계획을 구분해 기록한다.

## 1. 오늘 수업 핵심

- **기획서 리딩:** 규칙을 한 번 읽고 넘어가지 않고, 전체 읽기 → 반복 읽기 → 핵심 규칙 다시 읽기를 통해 누락·충돌·예외 조건을 찾는 연습.
- **상세명세서:** 기획서에 적힌 사실만 옮기는 것이 아니라, 구현과 테스트에 필요한 **조건·처리 결과가 명확하지 않은 부분을 문의**로 남기는 작업.
- **수치·데이터 확인:** 보상 순위 구간, 초기화 시간, 메타데이터 값 등 세부 조건을 읽으며 오타·범위 중복·기준 충돌 가능성을 확인.
- **실습:** 교육용 펫 시스템 Excel의 상세명세서 시트에 문의사항을 직접 작성. 실습 시간은 약 **3시간**.

강사님은 교육용 펫 시스템 기획서에서 **약 30개 정도의 문의 지점을 찾을 수 있다**고 안내했다. 나는 당시 약 12개 정도를 파악했으며, 사람마다 발견하는 범위에는 차이가 있을 수 있다고 이해했다. **문의 개수를 채우는 것보다 근거와 질문의 정확성을 우선**해야 한다.

## 2. 기획서 리딩에서 배운 질문 방식

### 규칙 충돌과 경계 조건 확인

- 다른 콘텐츠의 일일 초기화 시간이 **00시**인데 새 기획서에서 **05시**라고 한다면, 별도로 의도된 시간인지 또는 오기인지 확인.
- 보상 순위가 **301~500등**, **500~1000등**처럼 작성됐다면 **500등이 두 구간에 동시에 해당**하므로 어떤 보상이 적용되는지 확인.
- 메타데이터나 설정 테이블의 변수·수치가 본문 설명과 일치하는지도 확인. 값 자체는 있어도 서로 다른 기준이 혼재할 수 있음.

위 사례는 강의에서 제시된 **문의 작성 예시**이며, 특정 실제 서비스에서 해당 오류가 발생했다는 뜻은 아니다.

### 상세명세서 문의 작성 형식

1. **문의 내용:** 어떤 조건에서 무엇을 확인하려는지 짧게 작성. 가능하면 **한 줄 이내**로 정리하고 불필요한 종결 표현을 줄여 가독성 확보.
2. **예시·보충 설명:** 어떤 상황에서 규칙이 비어 있거나 모호한지 구체적인 수치·상태·행동을 제시.
3. **관련 기획서:** 시트와 대·중·소항목까지 적어 원문을 빠르게 찾을 수 있도록 구성.

강의 예시 — **보유 다이아가 필요 수량보다 부족한 경우**

- 문의 내용: 필요 수량 미달 시 보유 다이아 표시 색상 또는 별도 강조 처리 여부
- 상황 예시: 필요 다이아 100개, 보유 다이아 99개
- 확인할 결과: 수량이 부족할 때 빨간색 등으로 강조 표시하는지, 충분한 경우와 동일하게 표시하는지
- 관련 기획서 표기 예: `빙고이벤트_세부사항_빙고이벤트구성`

관련 기획서는 `펫 시스템_펫 기본 시스템_4) 기본사항_(8) 펫 AI_ㄴ_e`처럼 **실제 문서의 계층 구조를 따라 적는 내비게이션 역할**을 해야 한다. 서로 나란한 항목을 상위·하위 관계로 잘못 묶지 않도록 주의.

## 3. 펫 시스템 상세명세서 작성 실습

교육용 기획서의 **펫 기본 시스템·성장·합성·컬렉션** 영역을 읽고 문의사항을 작성했다.

처음에는 자동 소환의 편의성, 일반 등급과 상위 등급의 효과 구성, 영웅·전설 펫 컬렉션의 보상 가치 등 **유저 입장에서 기획이 적절한지**를 많이 생각했다. 반면 상세명세서를 작성할 때 더 직접적으로 필요한 것은 **기획대로 구현했을 때 어떤 동작이 정상인지 결정할 수 있도록 조건과 결과를 확인하는 질문**이었다.

실습하며 관심을 가졌던 사례:
- 자동·수동 소환이 이어지는 상황에서 펫 교체 처리가 어떻게 되는지
- 버프·고유 효과·액티브 스킬 용어와 적용 규칙의 구분
- 펫 스킬 모션 도중 귀환·이동 시 스킬 효과와 애니메이션 처리
- 동일 재료 여러 장 등록 시 합성 슬롯의 표시 방식
- 재뽑기 횟수 소진 및 확정 대기 기간 만료 시 결과 처리
- 성장 경험치의 누적값과 필요값, 관련 테이블 간 일치 여부

이 항목들은 **실습 중 작성하거나 검토한 문의 후보**이며, 실제 오류로 확인된 사항을 일괄 나열한 것은 아니다.

## 4. 강사님 피드백 — 가장 중요한 문제

강사님께서 주신 핵심 피드백은 다음과 같았다.

- 작성한 문의 가운데 **기획적인 관점의 평가**가 많음.
- “이 기획이 맞는가?”, “유저에게 불편하지 않겠는가?”는 **기획 개선·건의**에 가깝고, 이번 **상세명세서의 규칙 확인 문의**와는 성격이 다름.
- 상세명세서는 먼저 **동작 조건과 규칙 사이에 충돌이 있는지, 예외 상황에서 무엇이 발생하는지** 확인해야 함.
- 예: 자동 소환을 진행하는 중 수동 소환을 하면 어떻게 처리되는지 확인.

내가 잘못 접근한 부분은 **질문 자체를 떠올리지 못한 것보다, 의문이 생겼을 때 곧바로 기획의 적절성을 평가한 점**이다. 기획서를 읽으면서 “이렇게 만드는 것이 좋은가?”부터 생각했고, “이 조건에서 무엇이 발생한다고 명시되어 있는가?”를 충분히 확인하지 않았다.

## 5. 다른 수강생 작성본과 비교한 회고

수업에서 참고한 다른 수강생들의 상세명세서와 내 문서를 비교했다. **개인 이름과 작성 파일은 공개하지 않는다.**

| 비교 관점 | 내가 주로 했던 접근 | 참고할 점 |
| --- | --- | --- |
| 자동 소환 | 상황별 펫 교체가 불편하지 않을지 평가 | **A펫 소환 중 B펫으로 교체**할 때 주문서 소모·소환 시간·기존 펫 처리 확인 |
| 등급별 효과 | 일반 펫도 효과 10개를 갖는 설계가 적절한지 평가 | 등급별 **효과 개수 상한, 부여 조건, 적용 결과**가 명시됐는지 확인 |
| 펫 성장 | 수치가 이상하다는 느낌 또는 단순 계산 | 본문과 데이터 테이블의 **적용 기준·누적 계산·레벨 경계** 대조 |
| 펫 컬렉션 | 완성 난도 대비 보상이 낮아 보이는지 평가 | 컬렉션 완성 후 펫을 **합성 재료로 소모**하면 완료 상태·효과가 유지되는지 확인 |
| 조작·UI | 클릭/탭 용어와 편의성 검토 | 어떤 플랫폼·입력·수량·상태에서 어떤 버튼과 결과가 노출되는지 확인 |

다른 수강생들은 **조건을 구체적으로 설정하고 답변을 받으면 동작 기준을 확정할 수 있는 질문**을 상대적으로 더 많이 작성했다. 나 역시 UI나 예외 상황에 관심은 있었지만, 질문을 작성할 때 기획 평가와 규칙 확인을 섞는 경우가 있었다.

다른 사람의 문의가 모두 정답이라는 의미는 아니다. **질문의 양이나 표현을 모방하기보다, 해당 질문이 어떤 조건과 기대 결과를 확인하는지 배우는 것**이 이번 비교의 목적이다.

## 6. 나의 변화가 필요한 부분

### ① 기획 평가와 QA 문의를 구분하기

- 기획 평가: “자동 소환이 마지막 펫 재소환에만 쓰이면 유저가 불편하지 않을까?”
- 명세 문의: “A펫이 소환된 상태에서 수동으로 B펫을 선택하면 **기존 펫 해제, 주문서 소모, 남은 소환 시간**은 어떻게 처리되는가?”

첫 번째 생각도 게임 기획이나 UX 개선 제안에서는 의미가 있다. 하지만 **이번 상세명세서 실습에서는 두 번째처럼 동작 기준을 확정하는 질문을 우선**해야 한다.

### ② 하나의 조건을 바꾸어 보기

기획서의 정상 흐름만 읽지 말고 다음과 같이 조건을 바꿔 생각한다.

- **기존 상태가 있을 때:** 이미 소환된 펫이 있다면?
- **입력이 연달아 발생할 때:** 자동 소환 중 수동 소환을 하면?
- **조건을 충족하지 못할 때:** 재화·재료가 부족하면?
- **경계값에 도달할 때:** 횟수·수량·기간이 최대치이거나 만료되면?
- **상태가 바뀌는 도중:** 이동·귀환·접속 종료가 발생하면?
- **다른 기능에 영향을 줄 때:** 컬렉션에 사용한 펫을 합성 재료로 소모하면?

이 사례들은 **새 기능을 제안하는 목록이 아니라, 기획서에 결과가 명시되어 있는지 찾아볼 점검 관점**이다.

### ③ 질문 전에 관련 시트를 모두 확인하기

기본 시스템에 없는 내용이 성장·합성·컬렉션 또는 설정 데이터에 이미 있을 수 있다. 질문을 바로 적기 전에 **다른 시트에 답이 있는지 먼저 대조**한다. 값이 서로 다르다면 어느 테이블을 기준으로 하는지 묻는다.

### ④ 질문을 한 줄로 좁히기

질문 하나에 UX 개선, 설계 의도, 밸런스 평가, 동작 규칙을 모두 넣지 않는다. **문의 조건 → 미정의된 처리 결과**에 초점을 맞추고, 보충 설명에 비교 수치와 사례를 넣는다.

## 7. 다음 실습에서 적용할 점검 기준

질문을 기록하기 전에 스스로 확인할 네 가지:

1. **조건:** 언제, 어떤 상태에서, 누가 무엇을 하는가?
2. **근거:** 해당 내용이 기획서 어디에 있으며 관련 규칙을 모두 읽었는가?
3. **공백·충돌:** 어떤 처리 결과가 빠져 있거나 서로 다르게 적혀 있는가?
4. **답변 활용:** 답변을 받으면 상세명세서의 정상 동작 또는 향후 TC의 기대 결과로 옮길 수 있는가?

네 가지에 답할 수 없다면 우선 질문을 다듬는다. **기획의 적절성이나 UX 개선을 논의하는 의견은 별도로 구분**한다.

## 8. 오늘의 개인 회고

게임을 오래 플레이해 온 경험 때문에 기획서를 읽으면 자연스럽게 **“이 기능이 유저에게 편리할까?”, “이 보상이 충분할까?”**부터 떠오른다. 이런 시선은 게임을 분석할 때 도움이 되지만, 이번 QA 상세명세서 실습에서는 오히려 동작 규칙을 정확하게 확인하는 과정을 놓치게 했다.

강사님 피드백을 듣고 다른 수강생 문서를 비교하면서 **좋은 문의는 꼭 거창한 개선안이 아니라, 작은 조건 하나의 처리 결과를 명확히 묻는 것**이라는 차이를 이해했다. 다만 머리로 이해한 것과 다음에 스스로 발견하고 질문하는 것은 별개의 문제다. 아직 새로운 기획서를 혼자 읽을 때 같은 관점으로 접근할 수 있을지는 확신이 없다.

그래서 다음에는 질문 개수부터 늘리기보다 **기획서 규칙을 한 줄 읽고 조건을 바꾸어 보며, 누락된 결과를 찾는 연습**을 하려고 한다. 잘못 해석한 부분을 인정하고 관련 시트로 되돌아가 다시 확인하는 습관도 필요하다.
