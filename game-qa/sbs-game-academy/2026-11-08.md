# 2026-11-08 QA 수업 정리 — 기획 TC 작성 5단계와 펫 시스템 계층 정리

> 수업 화면과 개인 필기를 바탕으로 정리한 TIL. 강의에서 설명한 내용, 실습 안내, 강사 피드백, 앞으로 보완할 점을 구분한다.

## 1. 오늘 수업 핵심

- **기획 TC:** 수업에서는 게임 회사의 실제 개발·검증 과정에서 기획서를 기준으로 작성하는 TC와, 공개된 게임을 분석해 작성하는 포트폴리오용 **역기획 기반 TC**를 구분해 설명했다.
- **TC 작성 5단계:** 분류(Category) → 전제조건(Precondition) → 재현 순서(Step) → 기대값(Expected Result) → 결과값(Test Result).
- **계층 정리:** 기획서에 등장하는 기능과 규칙을 먼저 분류해야 이후 테스트 조건과 TC를 체계적으로 도출할 수 있다.
- **표현 원칙:** 작성자만 이해하는 생략과 중복 표현을 줄이고, 다른 사람이 읽거나 수행해도 이해할 수 있게 작성한다.
- **실습:** 교육용 펫 시스템 기획서와 상세명세서를 기준으로 **펫 기본 시스템, 펫 성장, 펫 합성, 펫 컬렉션**의 계층을 정리했다.

## 2. 1단계 — 분류(Category)

TC의 출발점은 검증 대상을 어떤 체계로 분류할지 정하는 것이다. 수업에서는 일반적인 예시로 **대분류 → 중분류 → 소분류**를 소개했다.

| 계층 | 수업에서 제시된 예시 |
| --- | --- |
| 대분류 | 가방, 캐릭터, 상점, 스킬 등 메뉴·시스템 단위 |
| 중분류 | 캐릭터 → 기사·마법사·군주·요정처럼 종류별 분류 |
| 소분류 | 기사 → 스킬·장비·이미지·모션처럼 하위 항목 |

중분류를 나누는 방법으로 **내용 기반**, **UI 영역**, **주요 기능** 기준을 소개했다. 다만 강의 이미지가 이전 업데이트 버전이어서 실제 분류 방식은 대상 게임과 기획서의 구조에 맞춰 판단해야 한다는 메모가 있었다.

최근 실무에서는 시트명에 콘텐츠명을 적고 대분류를 그 안의 하위 기능으로 잡는 방식도 사용한다고 설명했다. 중요한 것은 정해진 용어를 기계적으로 따르는 것보다 **어떤 기능이 어디에 속하고 어떤 관련 기능과 연결되는지** 이해하는 것이다.

이번 실습에서도 펫 기본 시스템뿐 아니라 성장·합성·컬렉션 시트를 함께 보며 구조를 정리해야 한다.

## 3. 2단계 — 전제조건(Precondition)

전제조건은 **테스트를 시작하기 전에 갖추어야 할 상태나 조건**이다.

수업에서는 모든 라인에 전제조건을 무조건 길게 기재할 필요는 없으며, **특정 상태를 요구하는 테스트에서 명확히 작성**한다고 설명했다.

예를 들어 '보스레이드 결과 화면을 확인하는 테스트'라면, 그 화면에 도달하기 위해 어떤 상태가 필요한지 먼저 적어야 한다. 필요한 경우 상위·중위·하위 그룹에 공통되는 조건을 구분해서 관리할 수 있다.

개인 메모: 동일한 기능을 확인하더라도 시작 상태가 달라지면 동작과 결과 해석이 달라질 수 있으므로, **어떤 상태에서 수행하는 TC인지** 먼저 생각해야 한다.

## 4. 3단계 — 재현 순서(Step)

재현 순서는 다른 사람이 **같은 테스트를 실제로 따라 할 수 있도록 조작을 순서대로 작성하는 것**이다.

수업에서 강조한 기준:

1. 작성자의 주관과 이미 알고 있다는 가정을 배제한다.
2. '메뉴 → 던전 → 보스던전'처럼 실제 이동 경로를 적는다.
3. 추상적인 '확인한다'만 쓰지 않고 **어디에 들어가 무엇을 조작하고 무엇을 확인할지** 명시한다.
4. 가능하면 기획서에서 사용하는 시스템·콘텐츠 명칭을 정확히 사용한다.

내가 아는 경로라도 다른 사람은 모를 수 있다. 따라서 **재현 가능한 절차**인지가 중요하다.

## 5. 4단계 — 기대값(Expected Result)

기대값은 **조건과 절차를 수행했을 때 기획서에 따라 나타나야 하는 결과**다.

수업에서 강조한 표현 기준:

- '버튼 클릭 시 버튼 효과가 출력되어야 합니다'처럼 같은 말을 반복하지 않는다.
- 가능하면 '클릭 시 버튼 효과 출력' 또는 '버튼 효과 출력'처럼 검증할 결과를 명확하고 간결하게 적는다.
- '정상적으로', '문제없이'처럼 구체적인 결과를 대신하지 못하는 표현을 줄인다.
- 서로 다른 조건의 결과를 한 문장에 겹쳐 쓰지 않는다.

수업의 표현 개선 사례:
- 개선 전: '몬스터 처치 시 골드가 정상적으로 획득된다.'
- 개선 후: '골드 획득'
- 개선 전: '몬스터 처치 시 명예 코인이 정상적으로 획득된다.'
- 개선 후: '명예 코인 획득'

단, **간결함만으로 충분한 것은 아니다.** 수량이나 범위가 검증 목적에 필요하다면 구체적인 기준이 있어야 한다. 수업 화면에서도 개발 QA 주의사항으로 **드랍 재화의 최소·최대 범위 검증 필요**가 제시되었다. 실제 기대 수치는 원본 명세서에 근거해야 하며 임의로 만들면 안 된다.

개인적으로는 '무엇을 확인할 것인지'가 한눈에 들어오면서도, 합격·불합격을 판단하는 데 필요한 정보가 빠지지 않도록 작성해야 한다고 정리했다.

## 6. 5단계 — 결과값(Test Result)

TC를 실제 수행한 후 결과를 기록하는 단계다. 강의 화면에서 다음 상태를 소개했다.

| 강의 화면 표기 | 의미 |
| --- | --- |
| Not Test | 테스트 미진행 |
| Blocker | 테스트 진행 불가 |
| Pass | 기대한 동작 확인 |
| Fail | 기대 결과와 다른 이슈 발생 |
| N/A | 해당 항목 제외 또는 적용 대상 아님 |

위 명칭은 **오늘 강의 화면의 표기**이며, 실제 프로젝트의 상태명은 팀에서 사용하는 규칙에 맞춰야 한다. 아직 실행하지 않은 기획 TC에 임의로 Pass나 Fail을 기록하지 않는다.

추가로 강의에서는 **마켓별 결과 관리**(AOS의 구글·원스토어·갤럭시, iOS의 애플)와 **원빌드 여부 확인**(원빌드와 개별 빌드의 결과 처리 차이)도 언급했다. 각 플랫폼과 빌드를 동일하게 취급할 수 있는지 확인해야 한다는 취지로 기록했다.

## 7. 오늘 실습 — 펫 시스템 계층 정리

실습 대상은 교육용 **펫 시스템**으로, 다음 네 영역을 함께 읽으며 계층을 정리하는 것이었다.

- 펫 기본 시스템
- 펫 성장
- 펫 합성
- 펫 컬렉션

수업 안내상 **엑셀 또는 구글 스프레드시트**로 작성했으며, 실습 시간은 **2시간 30분**으로 제시되었다. 제한된 시간 안에 마무리하는 것도 중요하다고 안내받았다.

예시로 '펫 성장 → 레벨 → 스킬 습득 → 가능/불가 → 1Lv·2Lv·3Lv·4Lv·5Lv'와 같이 **기능과 조건을 구분해 계층을 만드는 방향**을 보여 주었다. 이것은 계층 분류의 설명 예시이며, 모든 레벨에서 동일한 스킬 습득 규칙이 적용된다는 뜻은 아니다.

이번 실습에서 계층을 정리한 뒤, 이후에는 **기획서의 조건을 바탕으로 기획 TC를 작성하는 연습**으로 이어갈 예정이다. 계층 정리와 TC 설계를 구분해 진행한다.

## 8. 강사님 피드백과 개인 회고

강사님은 **열심히 작성한 점이 잘 보이고 전반적으로 잘했다**고 평가하면서도, **정리가 필요해 보인다**는 피드백을 주셨다.

함께 참고한 다른 수강생들의 계층정리 문서도 완성도가 높다는 이유보다, AI에 의존하지 않고 **기획서에 적힌 내용을 최대한 담으려 노력한 과정**을 중요하게 보셨다고 이해했다.

현재 내가 보완할 부분은 **규칙을 많이 옮기는 것에서 그치지 않고, 성격이 비슷한 항목을 적절한 계층에 묶어 보기 쉽게 정리하는 능력**이다. 다만 강사님이 말한 '정리'가 정확히 어떤 셀이나 분류를 뜻했는지는 추가 검토가 필요하다. 특정 항목이 잘못됐다고 단정하지 않겠다.

AI는 과제를 대신 완성하는 용도가 아니라, **내가 이해하지 못한 개념을 질문하거나 직접 작성한 계층의 중복·충돌을 확인하는 보조 수단**으로 사용하려고 한다.
